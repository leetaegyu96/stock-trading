# 매매 규칙서 (trading-rules) v2

이 문서는 시뮬레이터의 매매 판정 로직 **단일 기준 문서**다.
`simcore/config.py` 의 모든 설정값과 1:1 대응하며, 설정을 바꾸면 이 문서도 함께 갱신한다.
코드를 읽지 않아도 이 문서만으로 "왜 이 종목을 샀는지/팔았는지" 재구성 가능해야 한다.

- 최종 갱신: 2026-07-20 (의사결정판: 후보 기록·차단 사유·보유 상태 기록·생애 정의·리스크
  파생필드 출처 절 추가 — 감사 Phase B)
- 설계 스펙: `docs/superpowers/specs/2026-07-09-signal-system-v2-design.md`
- 튜닝 이력: 실험 결과는 `docs/experiments/` 참조

v1(청신호 개수 ≥ 7 / 적신호 개수 ≥ 3 카운트 방식)은 폐기되었다. v2는 **신호별 점수 + 카테고리
상한 + 매수 다중 게이팅 + 매도 등급 + 트레일링 스탑**으로 대체한다. 목표는 수익 극대화가 아니라
**손실 최소화**: 매수는 다중 확인을 요구해 까다롭게, 매도는 등급에 따라 빠르게 대응한다.

## 1. 판정 주기와 체결 규칙

| 단계 | 시점 | 하는 일 |
|---|---|---|
| 신호 판정 | 일봉 확정 시 (장 마감 후) | 유니버스 전 종목 청/적신호 점수·게이트 계산 → 매수/매도 예약 |
| 신호 주문 체결 | **다음 거래일 시가** | look-ahead bias 방지를 위해 당일 체결 금지 |
| 손절/트레일링 스탑 | 장중 5분마다 (라이브) / 일중 OHLC 근사 (리플레이) | 신호와 무관하게 즉시 체결 |

리플레이 일중 근사: 당일 고가로 peak(포지션 최고가)를 먼저 갱신한 뒤 잠금 손절선을 갱신하고,
당일 저가 ≤ 잠금 손절선(또는 트레일선)이면 트레일링 스탑 체결. **손절 우선**(보수적 처리)이며
기존 v1의 +15% 고정 익절(R10)은 트레일링 스탑으로 완전히 대체되어 더 이상 존재하지 않는다.

## 2. 신규 지표 (`simcore/indicators.py`)

기존 SMA·RSI·MACD·볼린저·스토캐스틱에 아래를 추가:

- **ADX, DI+/DI−** — 추세 강도/방향 (`adx_period=14`, `adx_threshold=25.0`)
- **일목균형표(Ichimoku)** — 전환선(9)·기준선(26)·선행스팬A/B(→구름, 52) (`ichimoku_tenkan=9`,
  `ichimoku_kijun=26`, `ichimoku_senkou_b=52`)
- **Parabolic SAR** — 추세 반전 추적 (`sar_af_step=0.02`, `sar_af_max=0.2`)
- **OBV(On-Balance Volume)** — 누적 거래량 방향
- **VWAP(롤링)** — 거래량 가중 평균가 (`vwap_period=20`)
- **ATR(Average True Range)** — 변동성 (`atr_period=14`)

## 5. 점수 계산 (카테고리 상한)

각 신호는 점수를 갖고, **카테고리별 상한**(`SignalScores.caps`)을 적용한 뒤 합산한다
(같은 계열 신호 과다 가중 방지). `총점 = Σ min(카테고리 점수합, 카테고리 상한)`. 청신호(매수)/
적신호(매도) 각각 독립 계산한다.

| 카테고리 (청 / 적) | 상한 |
|---|---|
| 추세 | 10 |
| 돌파(청) / 하락패턴(적) | 10 |
| 거래량 | 8 |
| 모멘텀 | 8 |
| 변동성 | 6 |

### 5-1. 신뢰도(confidence) — 정규화 신호 강도 (#31)

의사결정판(후보 테이블)에는 `green_score`/`red_score` 원점수 외에 **신뢰도**를 함께
표시한다. `signal_confidence(score, scores, side)`(`simcore/signals.py`)가 계산하며,
정의는 다음과 같다.

- `MAX(side) = Σ caps[cat]` — 해당 side(청/적)의 코드가 속한 **카테고리들의 상한 합**
  (하드코딩 아님, `SignalScores.category`/`caps`에서 매 호출 시 동적 계산). 현재 설정값
  기준 청/적 모두 추세10 + 돌파(또는 하락패턴)10 + 거래량8 + 모멘텀8 + 변동성6 = 42.
- `confidence = round(min(1.0, max(0.0, score / MAX)), 2)` — 0~1로 클램프 후 반올림.
- 저장된 `green_score`/`red_score`(이미 DB에 기록된 값)로부터 **읽기 시점에만 계산하는
  순수 파생값**이다. 새 DB 컬럼 없음, 엔진·매수/매도 판정에는 전혀 관여하지 않는다(표시
  전용).
- **고정 익절 타깃(예: "목표수익률 r*")은 제공하지 않는다** — 본 전략은 §8 트레일링
  스탑 기반이라 고정 타깃 개념이 없고, 없는 것을 지어내면 정직 라벨링 원칙에 어긋난다.
  진입 손절폭(`stop_loss_pct`)과 보유 종목의 `stop_px`/`stop_distance_pct`(§16-5)는 이미
  노출되어 있으므로 confidence는 그 외에 "신호가 얼마나 강하게 발화했는가"만 보여준다.

## 6. 매수 규칙 (다중 게이팅) — `buy_score_min=18`

점수 등급(표기용):

| 총점 | 등급 |
|---|---|
| 12+ | 관심 (`buy_score_interest`) |
| 15+ | 후보 (`buy_score_candidate`) |
| 18+ AND 게이트 충족 | **매수** (`buy_score_min`) |

**실제 매수는 총점 ≥ 18 AND 아래 3개 게이트 집합에서 각 1개 이상 발화**(`SignalScores.buy_gate`):

- **추세**: G1 · G4 · G11 · G12 · G15 중 1개 이상
- **돌파**: G7 · G18 중 1개 이상
- **거래량**: G5 · G13 · G23 중 1개 이상

우선순위(현금·슬롯 배분): 총점(green_score) 내림차순 → 당일 등락률 → 거래량.

하락장 가드: 캐릭터별 스위치 `bear_guard_characters`(기본 **전체 off**, 빈 집합). CLI
`--bear-guard`(전체 강제 on) / `--no-bear-guard`(전체 강제 off)로 opt-in/opt-out. 상세는 §6-1,
튜닝 결과는 §6-1 말미 참조.

### 6-1. 하락장 가드 v2 (시장 지수 추세 필터 — 캐릭터 전 시장 하락 시만 차단)

시장 대표 지수(국내=코스피200, 해외=S&P500)의 **이동평균**을 매일 계산해 시장별 하락장 여부를
판정한다. SMA 기간은 시장별로 독립 설정한다: `market_trend_period_kr`(기본 20) ·
`market_trend_period_us`(기본 20). 이 기간은 캐릭터가 가드 대상으로 opt-in됐을 때만 쓰인다.

- **판정**: 지수 종가 < 지수 해당 시장 SMA → 해당 시장 **하락장**.
- **차단 조건(v2)**: `st.spec.name in bear_guard_characters` **AND** **캐릭터가 거래하는 모든
  시장이 하락장일 때만**(`all(bearish_by_market[m] for m in 캐릭터.markets)`) 그 캐릭터의
  신규 매수를 차단한다. 즉 가드는 캐릭터 단위로 켜고 끄며(`bear_guard_characters`에 캐릭터
  이름이 있어야 판정 자체가 걸린다), 켜진 캐릭터에 대해서만 위 시장 하락 조건을 본다.
  - **단일시장 캐릭터**(국내형=KR만, 해외형=US만): 가드가 켜져 있고 자기 시장이 하락장이면
    즉시 차단 — v1과 동일하게 동작(단일시장 캐릭터는 v1·v2 리플레이 결과가 완전히 동일함 —
    `docs/experiments/replay_bear_guard_ab_2026-01-09_2026-07-09.md` A/B 참고).
  - **범용형**(KR+US 양시장): 가드가 켜져 있을 때 **두 시장이 동시에 하락장일 때만** 차단한다.
    한쪽 시장만 하락해도 차단하지 않는다 — v1은 한쪽 시장만 하락해도 전체를 막아 과발동했던
    문제를 해소한 것이 v2의 핵심 변경.
- **적용 범위**: 신규 매수만 차단한다. 이미 보유 중인 종목의 매도·손절·트레일링 스탑은
  영향받지 않고 그대로 동작한다(리스크 관리 로직은 시장 추세와 무관하게 항상 작동).
- **기본값**: `bear_guard_characters=frozenset()`(전체 off) — 지수 데이터가 없거나 로드되지
  않은 경우에도 가드는 발동하지 않는다(안전한 기본 동작).
- **활성화**: CLI 리플레이 실행 시 `--bear-guard` 플래그로 전 캐릭터 강제 on, `--no-bear-guard`로
  전체 강제 off한다(둘은 상호 배타). (`python -m simcore ... --bear-guard`) 특정 캐릭터만
  적용하려면 `Config.rules.bear_guard_characters`에 캐릭터 이름 집합을 지정한다.
- **튜닝 결과(2026-01-09~2026-07-09 스윕 + 12개월 검증)**: `market_trend_period_kr/us`를
  20·40·60·120일로 스윕하고 채택 규칙(TWR≥OFF−1%p AND MDD 개선 → MDD 최소)을 적용한 뒤
  12개월 창(2025-07-10~2026-07-09)에서 재검증했다. 결과, **국내형은 가드를 걸면 모든 기간에서
  TWR이 OFF보다 낮아** 가드 대상에서 영구 제외 권장. 해외형·범용형은 6개월 창에서는 MDD가
  개선되는 후보(둘 다 kr=20,us=20)가 나왔지만, 12개월 창에서는 **두 후보 모두 MDD가 OFF보다
  악화**되어 스펙 §1의 검증 게이트(MDD 개선 방향 유지)를 통과하지 못했다. 6개월 단일 창의
  개선은 그 구간 특유의 국면에 대한 과적합이었던 것으로 판정한다. 이에 따라 **기본값은 전체
  off로 확정**됐고, 국면 판단이 서면 향후 `--bear-guard` 또는 특정 캐릭터 집합으로 opt-in할 수
  있도록 인프라(캐릭터별 스위치 + 시장별 기간)만 남겨둔다. 상세 데이터와 근거는
  `docs/experiments/bear_guard_tuning_sweep_2026-01-09_2026-07-09.md` 참고.

## 7. 매도 규칙 (등급) — `sell_partial_min=9` / `sell_full_min=11`

적신호 총점(red_score) 기준:

| 총점 | 조치 |
|---|---|
| 0~5 | 보유 |
| 6~8 | 주의(보유, 기록만) |
| 9~10 | **부분 매도**(보유 수량의 `partial_sell_fraction`=50%) |
| 11+ | 전량 매도 |

**강제 매도**(점수 무관, 즉시 전량):
- R7 — 잠금 손절 도달
- 트레일링 스탑 발동(R10)
- R18 — 지지선(최근 저점) 붕괴
- R5 + R23 동시 발화 — 거래량 급증 음봉 + 장대 음봉

부분 매도는 포지션을 남기므로 **쿨다운 없음**(평단·피크 유지). 전량 매도(등급/강제 불문)는
**쿨다운 2거래일**(`cooldown_days`) 적용.

### 7-1. 점수 매도 토글 — `signal_sell_enabled` (기본 `True`)

`False` 로 두면 **위 등급표(9점 부분/11점 전량)만 비활성**되고, 바로 위의 **강제 매도 4종
(R7 손절 · R10 트레일링 · R18 지지선 붕괴 · R5+R23 급락 복합)은 그대로 유효**하다. 매수 경로도
영향받지 않는다. 이른바 **"손절/트레일만" 모드**.

운영에서는 코드 수정 없이 `.env` 의 `SIGNAL_SELL_ENABLED` 로 전환한다(`INTRADAY_ENABLED` 과 동일
관용구, `simcore/live/settings.py` → `_config_from_settings`). 동시 보유 종목 수도
`MAX_POSITIONS` 로 덮어쓸 수 있다(기본 `max_positions`=5).

**근거** — `docs/reviews/2026-09-02-live-loss-autopsy.html`. 2026-07-21~09-02 라이브에서 손실은
전부 점수 매도 구간(특히 red≥11 전량매도: KR −673만원)에서 나왔고, 부분매도 구간(9~10점)은
양 시장 모두 흑자였다. 같은 유니버스 3.2년 리플레이에서 점수 매도를 끄고 보유를 10종목으로
넓힌 구성이 3구간 워크포워드 9칸 중 수익률 7칸 · MDD 8칸에서 우세했다. 임계값을 13/16/26 으로
올리는 방식은 캐릭터별로 결과가 뒤집혀 과적합으로 판단해 채택하지 않았다.

> 주의: 같은 유니버스의 동일가중 바이앤홀드(KR +412% / US +97%, 생존편향 포함)는 이 구성으로도
> 넘지 못한다. 이 토글은 **기존 규칙 대비** 개선이지 알파의 증명이 아니다.

## 8. 트레일링 스탑 (v1의 +15% 고정 익절을 대체)

포지션별로 진입 후 **최고가(peak)**와 **잠금 손절 등급(locked stop, 평단 대비 %)**을 추적한다.
초기 잠금 손절 = `stop_loss_pct`(−7%). peak 수익률이 아래 구간을 넘으면 잠금 손절을 상향(락인):

| peak 수익률 도달 | 잠금 손절(평단 대비) |
|---|---|
| +10% | 0% (본전) |
| +20% | +10% |
| +30% | +20% |
| +40% | +30% |
| `trailing_top`=+40% 초과 | 최고가 대비 −`trail_pct`(7%) 트레일 |

(`TradeRules.trailing_tiers = ((0.40, 0.30), (0.30, 0.20), (0.20, 0.10), (0.10, 0.0))`, 내림차순
첫 매칭 적용.)

- 매 판정(종가) / 5분(라이브) 체크 시: peak 갱신 → 잠금 손절 갱신 → 현재가 ≤ 잠금 손절선
  (또는 +40% 초과 구간의 최고가 트레일선)이면 **전량 매도**(사유 = 트레일링 스탑, R7/R10).
- 초기 −7% 손절(R7)은 잠금 손절의 시작값으로 자연 포함된다.

## 9. 포지션 사이징 · 우선순위

- 최대 보유: 캐릭터당 **`max_positions`=5종목**.
- 1종목 배분: `가용 현금 ÷ 남은 슬롯 수` 균등 배분.
- 매수 우선순위: green_score 내림차순 → 당일 등락률 높은 순 → 거래량 많은 순.
- 현금 부족 시 매수 스킵. 매도로 현금이 생기면 다음 판정 주기에 후보 매수.
- 이미 보유 중인 종목 재매수 금지.
- **쿨다운**: 전량 매도한 종목은 **`cooldown_days`=2거래일** 재매수 금지. 부분 매도는 쿨다운 없음(§7).
- 범용형은 같은 날 국내·미국 후보가 함께 있으면 국내 시장을 먼저 처리한다(슬롯·현금을 KR 이 우선 소비). 결정론적 처리 순서이며 별도 우열 규칙은 아니다.

### 10-1. 환전 정책 — 부족분만 (v1.18.0)

두 시장을 다 쓰는 캐릭터(범용형)는 **매도 대금을 그 통화 그대로 보유**한다. 매수 때
`Portfolio.buying_power(cur, fx)` 로 **양 통화를 합산한 여력**을 계산하고, 체결에는 보유
통화를 먼저 쓴 뒤 `ensure_cash` 로 **부족분만** 환전한다. 출금도 원화가 모자랄 때만 부족분을
달러에서 메운다.

예전에는 US 매도마다 `convert_all_usd_to_krw` 로 달러 전액을 원화로 되돌렸고, 다음 US
매수에서 다시 달러로 바꾸느라 **왕복 0.2%** 를 물었다. 라이브 6주에 약 160만원, 3.2년
리플레이 기준 총 회전액으로 환산하면 초기자본의 5.0%p 규모였다.

수정 후 범용형 성과(같은 유니버스, 국내형·해외형은 단일 통화라 **불변** — 대조군):

| 구간 / 규칙 | 수정 전 | 수정 후 |
|---|---|---|
| 3.2년 · 현행 규칙 | −5.4% / MDD −41.3% | **+2.7%** / MDD −37.7% |
| 3.2년 · 현재 운영구성 | +89.0% / MDD −15.3% | **+90.2%** / MDD −15.2% |
| 2026년 8개월 · 현재 운영구성 | +17.1% / MDD −9.3% | **+18.1%** / MDD −9.2% |

회수액이 위 5.0%p 추정보다 작은 이유는, 시장 간 순이동분은 어차피 환전해야 하므로 **왕복
중복분만** 사라지기 때문이다. `convert_all_usd_to_krw` 자체는 청산·명시적 전량 환전용으로
남아 있다.

## 12. 사용자 입출금 규칙

- 사용자는 언제든 캐릭터별로 자금을 추가 입금하거나 출금할 수 있다.
- 입금: 현금 잔고에 즉시 반영. 해외형은 당일 환율 환전(환전 수수료 적용).
- 출금: 현금이 충분하면 즉시 차감. **부족하면 엔진이 자동 매도하지 않고**,
  사용자가 청산할 보유 종목을 직접 선택해 매도한 뒤 출금한다.
  이 매도는 거래내역에 `사유=사용자 출금` 으로 기록되며 수수료·세금이 동일하게 붙는다.
- 수익률은 입출금 왜곡을 제거한 **시간가중수익률(TWR)** 로 표시하고,
  누적 손익 금액(원)을 참고 지표로 병기한다.
- 사용자 출금으로 전량 매도된 종목도 쿨다운(2거래일 재매수 금지)이 동일하게 적용된다.

## 13. 결정 유형(DecisionType)과 표시 규칙

거래마다 엔진이 **결정 시점(그날의 판정/체결 처리 중)**에 `DecisionType`(`simcore/models.py`)과
`trigger_rule`을 확정해 트레이드에 영속한다. 이후 리플레이 DataFrame, 라이브 DB `TradeRow`,
시드(seed_from_replay)는 이 값을 그대로 옮겨 담을 뿐 재계산하지 않는다.

| DecisionType | 의미 | trigger_rule 규약 |
|---|---|---|
| `BUY` | 매수 체결 | `"게이트+N점"` (N = 매수 확정 시 green_score) |
| `PARTIAL_SELL` | 부분 매도(§7 등급, 9~10점) | 발화한 적신호 코드를 `+`로 join (예: `"R2+R6"`) |
| `FULL_SELL` | 전량 매도(§7 등급 11+, 또는 비신호성 사유) | 등급 매도는 발화 적신호 join. **사용자 출금**(§12)·**상장폐지**는 신호가 원인이 아니므로 trigger_rule과 fired 모두 공백으로 둔다 |
| `FORCED_SELL` | 강제 전량 청산(점수 무관, §7 강제 매도) | `R7` / `R18` / `R5+R23` / `R10` 4종 중 하나 |

**강제 매도 트리거 4종** (등급을 건너뛰고 즉시 전량):
- `R7` — 잠금 손절 도달
- `R18` — 지지선(최근 저점) 붕괴
- `R5+R23` — 거래량 급증 음봉 + 장대 음봉 동시 발화(급락 복합조건)
- `R10` — 트레일링 스탑 발동

**표시 매핑** (`simcore/signal_display.py::summarize()`)은 영속된 `decision_type`/`trigger_rule`을
문구로 옮길 뿐, red_score/green_score를 다시 계산해 결정을 재구성하지 않는다(**표시는 변환만,
점수 재계산 금지** — 감사 Phase A 핵심 원칙):

| decision_type | 표시 문구 |
|---|---|
| `FORCED_SELL` | `"{원인 문구} → 강제 전량매도"` — 원인 문구는 trigger_rule → 급락 복합조건(R5+R23) / 지지선 붕괴(R18) / 잠금 손절선 도달(R7) / 최고가 대비 트레일링선 도달(R10) 4종 매핑 |
| `PARTIAL_SELL` | `"{발화 적신호명 최대3개} → 부분 매도 (적신호 N점)"` |
| `FULL_SELL`(등급, 적신호 있음) | `"{발화 적신호명 최대3개} → 전량 매도 (적신호 N점)"` |
| `FULL_SELL`(사용자 출금/상장폐지 — trigger_rule·fired 모두 공백) | `"신호 없음"` — 신호 문구를 조작해내지 않는다. 실제 사유(사용자 출금/상장폐지)는 화면의 `reason` 필드가 별도로 표시한다 |
| `BUY` | `"{발화 청신호명 최대3개} → 매수 후보/매수 신호/강력 매수 신호 (N점/등급)"` |

## 14. 위험조정 지표 · 벤치마크

`simcore/metrics.py::risk_metrics()`가 계산하는 지표. **무위험수익률은 항상 0으로 가정**한다.
CAGR·변동성·Sharpe·Sortino·Calmar는 자산곡선(equity)의 일간수익률 기반, 나머지는 거래내역의
**SELL(실현손익) 행 기준**(`realized_pnl`, side 컬럼이 있으면 SELL만 필터)이다.

| 지표 | 정의 |
|---|---|
| CAGR | `(V_마지막/V_처음)^(252/일수) − 1` |
| 변동성 | 일간수익률 표준편차(ddof=0) × √252 |
| Sharpe | (일간수익률 평균 × 252) / 변동성 (무위험 0) |
| Sortino | (일간수익률 평균 × 252) / (하락편차 × √252), 하락편차 = 음의 일간수익률만의 표준편차 |
| Calmar | CAGR / \|MDD\|. **MDD=0(낙폭 없음)이면 측정불가 → 0 반환**(CAGR로 대체하지 않음) |
| ProfitFactor | SELL 실현손익 중 이익 합 / \|손실 합\| |
| 평균손익(avg_win/avg_loss) | SELL 실현손익 중 이익/손실 각각의 평균(손실은 절대값) |
| 손익비(win_loss_ratio) | avg_win / avg_loss |
| 기대값(expectancy) | SELL 실현손익 전체 평균 |
| 최대연속손실(max_consecutive_losses) | 실현손익이 연속으로 음수인 최대 횟수 |
| 회복기간(recovery_days) | MDD 저점 이후 직전 고점을 회복하기까지의 일수(미회복이면 마지막 시점까지의 일수) |

**벤치마크**: 국내형=코스피200, 해외형=S&P500, **범용형(양시장)=두 지수 구간수익률의 단순평균
("혼합")** — 한쪽 지수만 있으면 그 지수 값·이름을 그대로 쓴다. 초과수익 `delta = TWR − 벤치마크
수익률`. 벤치마크는 리플레이/시딩 시점에 `BenchmarkRow`로 미리 계산해 저장하며, 대시보드는 요청
시점에 재계산하지 않고 저장된 값만 읽는다.

**벤치마크 미수집 시 경고 표시(숨김 금지)**: `BenchmarkRow`가 없거나(`benchmark_available=False`)
있어도 `benchmark_return`이 `None`(지수 데이터 미로딩 — 예: 하락장 가드가 꺼져 있어 리플레이/시딩이
지수를 로드하지 않은 경우)이면 `delta`도 `None`이 된다. 두 경우 모두 화면은 벤치마크 값을 조용히
숨기지 않고 "벤치마크 미수집" 경고를 표시해야 한다.

**"검증됨" 라벨 사용 금지**: 위험지표·벤치마크 근처에서 전략이 "검증됨"이라는 표현을 쓰지 않는다.
최소 3개 시장 국면(상승/하락/횡보)의 리플레이를 통과하기 전까지는 어떤 지표 값도 검증 완료를
의미하지 않는다.

## 15. 신호 라벨 규칙

화면에 노출하는 신호 표기는 항상 **"기술적 매수/매도 신호"**로 통일한다. 내부 용어인
"청신호/적신호"는 사용자 화면에 그대로 노출하지 않는다.

뉴스·공시·수급·거시 지표는 이 시뮬레이터가 계산하지 않는다(§3/§4의 미구현 스텁 참고. G8/G9는
#27에서 가격 지표(괴리율·지지저항) 기반 실신호로 전환되어 더 이상 뉴스·수급 스텁이 아니다).
신호가 보이는 모든 화면에는 "뉴스·공시·수급은 현재 판단에 반영되지 않음" 고지와, 계산되지 않은
축은 0점으로 위장하지 않고 **"미수집/판단 불가"** 레전드로 함께 표시한다.

## 16. 의사결정판(Decision Board) 관찰 기록 — 감사 Phase B

대시보드 의사결정판(후보/보유/생애 화면)이 읽는 관찰 데이터의 생성·저장 규칙. **이 절은 관찰
기록 추가일 뿐, §1~§9의 매매 판정·체결 로직 자체는 전혀 바뀌지 않았다** — 같은 입력이면 여전히
같은 거래가 나온다. `SignalStatusRow`(`simcore/live/db.py`)가 저장소이며, 값은 엔진의 기존
조건 분기(`Engine.evaluate_close` / `Engine.fill_open`, `simcore/engine.py`)를 그대로 따라가며
기록만 곁들인다.

### 16-1. 후보 기록

매 마감(장 마감 신호 판정, §1)마다 캐릭터별로 그 시장 유니버스 전 종목에 대해 매수후보 평가를
관찰 전용으로 기록한다(`kind="후보"`, `CandidateEval` → `SignalStatusRow`). 상태는 둘 중 하나:

- **`"예약"`** — 다음 개장에 매수 주문으로 넘어감(§1 신호 주문 체결 대기열에 실제로 들어간 종목).
- **`"차단"`** — 아래 §16-2 사유 중 하나로 그 마감에서 매수하지 않음.

### 16-2. 차단 사유(`block_reason`) — 정확한 값과 판정 단계

| 값 | 판정 단계 | 조건(코드 근거) |
|---|---|---|
| `"보유중"` | 마감 평가(`evaluate_close`) | 이미 보유 중이거나 이번 마감에 이미 매수 예약된 종목 |
| `"쿨다운"` | 마감 평가(`evaluate_close`) | 전량 매도 쿨다운(§9, `cooldown_days`) 중인 종목 |
| `"점수부족"` | 마감 평가(`evaluate_close`) | green_score < `buy_score_min`(18) |
| `"게이트미충족"` | 마감 평가(`evaluate_close`) | green_score ≥ 18이지만 §6 3개 게이트 집합 중 어느 것도 미발화 |
| `"슬롯부족"` | 개장 체결(`fill_open`) | 매수 우선순위 처리 중 `max_positions`(5) 슬롯 소진 |
| `"가격없음"` | 개장 체결(`fill_open`) | 개장 시가(`opens`)가 없음(거래정지 등) |
| `"현금부족"` | 개장 체결(`fill_open`) | 배분 현금으로 최소 1주도 매수 불가 |

마감 평가 4종은 종목별로 위 표 순서대로(보유중 → 쿨다운 → 점수부족 → 게이트미충족) 첫 번째
해당 사유가 확정되며, 조건을 통과하면 `status="예약"`으로 매수 대기열에 들어간다. 개장 체결 3종은
그 대기열을 우선순위(green_score 내림차순 → 등락률 → 거래량)로 소비하면서 판정되고, 확정되면
`status="차단"`으로 **덮어쓰기**된다(§16-1 "예약"이 실제 체결 실패 시 사후 갱신).

### 16-3. 보유 상태 기록

보유 중인 종목은 마감마다 `kind="보유"` row로 기록되며 다음 필드를 채운다:

- **`red_score`** — 그 마감의 적신호 점수(§4~§5). **라이브 경로에서** 이번 마감 유니버스 프레임에 그 종목의
  스냅샷이 없으면(랭킹 이탈 등으로 데이터가 없음) **직전 `signal_status`(kind=보유) 행의
  red_score를 그대로 승계**한다(0으로 리셋하지 않음 — 신호 데이터 부재를 "무위험"으로
  오인시키지 않기 위함). 직전 행조차 없으면(첫 마감 등) 0. 리플레이/시드 데이터에서는 유니버스 미포함 보유 종목의 red_score가 0으로 기록될 수 있다(승계 미적용).
- **`stop_px`** — `avg_price × (1 + locked_stop_pct)`(§8 잠금 손절선).
- **`trail_px`** — peak 수익률(`peak_price/avg_price − 1`)이 `trailing_top`(+40%)에 도달했을
  때만 `peak_price × (1 − trail_pct)`로 채운다. 미도달이면 `None`(아직 트레일 구간이 아니므로
  해당 없음을 그대로 노출).
- **`close`** — 그 마감 시점 저장 종가. §16-5 파생필드 계산의 기준값이자 `as_of`(그 행의
  `date`)와 짝을 이뤄 "언제 기준 값인지"를 함께 보증한다.

### 16-4. 생애(lifecycle) 정의

`position_lifecycles`(`dashboard/backend/queries.py`)는 캐릭터의 전체 거래 이력을 시간순으로
훑어 종목별 생애를 다음 규칙으로 그룹핑한다:

- 그 종목의 보유수량이 **0인 상태에서 BUY**가 오면 새 생애를 시작한다(`entry_date`=그 거래일,
  `entry_trigger`=그 BUY의 `trigger_rule`).
- 이후 SELL은 수량을 줄이고, 보유수량이 **0(또는 초과매도로 그 이하)에 도달하면 그 생애를
  종료**한다(`exit_date`=그 거래일, `open=False`). 청산 후 재매수는 완전히 별개의 새 생애.
- **orphan SELL**(대응하는 시작 BUY 없이 나타나는 매도 — 예: 시딩 이력이 중간부터 시작하는
  경우)은 어떤 생애에도 속하지 못하므로 **생애 뷰에서 제외**된다(크래시 방지 + 정합성 방어 —
  존재하지 않는 진입을 조작해내지 않는다).
- **`limit`은 하한이다.** 진행 중(open=True)인 생애는 개수와 무관하게 **항상 전부** 반환하고,
  남은 자리만 최근 진입일순 종료(closed) 생애로 채운다. 즉 open 생애가 `limit`을 넘어도 전부
  반환되며 잘리지 않는다(진행 중인 리스크를 화면에서 누락시키지 않기 위함).

### 16-5. 리스크 파생필드 출처

`positions` 응답(`PositionOut`, 의사결정판 확장 필드)의 파생값은 출처가 둘로 나뉜다:

- **`stop_distance_pct`**(`(close − stop_px) / close`) **· `potential_loss`**(수량 ×
  `(close − stop_px)`, 미국 종목은 원화 환산) — §16-3에서 **저장된 마감 종가(`signal_status.close`)**
  기준으로 계산한다. 요청 시점에 재계산하지 않으며, 응답의 `as_of`(그 signal_status 행의 date)와
  항상 같은 시점의 값이다(as_of 시점 일관성 보증 — 실시간 시세와 섞이지 않음).
- **`weight_pct`**(총자산 대비 비중) **· `current_price`**(포지션 평가에 쓰이는 현재가) — 요청
  시점 **라이브 평가**다. KIS 실시세(있으면)를 병합한 현재가·현재 총자산 기준으로 매 요청마다
  다시 계산된다.

캐릭터 상세 화면의 **차트 구간 수익률은 단순 수익률**(`metrics.simple_pnl_krw` 계열, 입출금
왜곡 미보정)이며, **입출금을 보정한 시간가중수익률(TWR)은 별도 지표 패널**(`Metrics.twr`,
§12·§14)에서 제공한다. 두 값을 같은 자리에서 혼용하지 않는다.

## §17 장중 자동매매(인트라데이)

라이브 페이퍼 서버가 **장중(개장~마감 사이)에도** 유니버스를 재평가해 즉시 매수/매도하는
루프. **일봉(마감) 로직과 완전히 병렬로 존재**하며, 마감 처리·리플레이·백테스트는 이 절의
영향을 받지 않는다.

**플래그(기본 OFF)**: `Config().rules.intraday_enabled = False`가 기본값이다. OFF인 동안은
신규 경로(스케줄러 잡 등록·오케스트레이터 `on_intraday`·엔진 `evaluate_intraday`)에 전혀
진입하지 않으며, 기존 엔진·리플레이·동치성·전체 pytest가 무수정으로 통과한다. 운영 서버에서
켜려면 별도 설정/환경변수로 명시적으로 `True`로 바꿔야 한다.

**10분 스캔·장시간 가드**: 활성화 시 `LiveScheduler`가 시장별로 `intraday_scan_minutes`(기본
10분) 간격 인터벌 잡을 등록한다(`simcore/live/scheduler.py::_guarded_intraday`). 이 잡은
① 그날이 거래일이고 ② 현재 시각이 그 시장의 **개장~마감 시간대 안**일 때만
`Orchestrator.on_intraday(...)`를 호출한다 — 장 마감 후·휴장일에는 실행되지 않는다.

**잠정봉(provisional bar)**: `Orchestrator.on_intraday`는 매 스캔마다 종목별로 다음을
조합해 하루짜리 "잠정 오늘 봉"을 만든다:
- **확정 히스토리**: 어제(d-1)까지의 일봉(`_refresh_bars`) — 당일 확정 일봉을 절대 오염시키지
  않도록 오늘 이전까지만 조회한다.
- **당일 관측치**: 현재가(`open`/`high`/`low`는 그날 첫 관측 이후 갱신되는 장중 고저,
  `close`=현재가), 당일 누적거래량(`daily_bars(d,d)` 조회, 실패 시 히스토리 마지막 거래량 대용).

이 잠정봉을 히스토리 뒤에 append한 프레임을 기존 `evaluate_frame`/`snapshot_scores`에
그대로 통과시켜 청/적신호·점수·게이트를 계산한다 — **일봉 매매와 동일한 신호 계산 로직을
재사용**하며 별도 신호 체계를 만들지 않는다. 단, 발화 추출은 `fired_at` 이 아니라
**`fired_at_provisional`** 을 쓴다(아래 §17-1).

### §17-1. 잠정봉의 거래량 왜곡과 그 처리

잠정봉의 `volume` 은 당일 **누적**(부분)인데, 지표가 비교하는 전일 거래량·20일 평균은
**완성된 하루치**다. 좌변만 부분값이라 이를 직접 비교하는 신호는 장중에 판정이 성립하지
않는다. 해당 신호는 `signals.VOLUME_SCALE_DEPENDENT` = **{G5, G23, R5, R24}** 이며,
`fired_at_provisional` 이 이들을 **미발화 처리**한다(값을 추정해 지어내지 않는다).

실측(일봉 3,278 종목일, 개장 30분=누적 10% 를 마감과 대조) — 왜곡되는 신호는 이 넷뿐이고
나머지 33개는 판정 뒤집힘 0.0% 다:

| 신호 | 장중 | 마감 | 판정 뒤집힘 |
|---|---|---|---|
| R24 거래량 감소 상승 | 49.5% | 22.7% | **26.8%** |
| R5 거래량 급증 음봉 | 0.0% | 3.3% | 3.3% |
| G5 거래량 급증 양봉 | 0.0% | 3.0% | 3.0% |
| G23 신고가+거래량 | 0.0% | 0.7% | 0.7% |

OBV(G13/R13)는 방향이 종가차 부호로만 결정돼 거래량 배율에 **불변**이고, VWAP(G14/R14)도
0.0~0.1% 라 제외 대상이 아니다.

**이 처리의 한계 — 오차가 사라지지 않고 부호가 뒤집힌다.** R24 가 정당하게 발화하던 22.7%
의 경우까지 4점을 잃기 때문이다. 마감 확정봉을 정답으로 놓으면:

| | 적신호 평균 | 전량매도 발동률 | 매수 게이트 통과 |
|---|---|---|---|
| 마감(확정봉) | 11.01점 | 50.5% | 8.18% |
| 장중 — 수정 전 | 12.01 (+1.00) | 61.9% (**+11.4%p**) | 8.18% |
| 장중 — 수정 후 | 10.03 (−0.98) | 37.2% (**−13.3%p**) | 8.18% |

수정 전은 **과매도**(실제 손실의 원인), 수정 후는 **과소매도**이고 후자는 매일 마감의 확정봉
판정(`on_close`)이 바로잡는다. 강제매도(R7/R10/R18)는 이 필터와 무관하게 유효하며, 매수
게이트 통과율은 8.18% 로 완전히 동일하다 — 거래량 관문 {G5,G13,G23} 은 실질적으로 G13 이
담당한다(라이브 매수 105건 **전부**가 G13 으로 통과).

오차를 실제로 줄이려면 **시간대별 거래량 프로파일**(장중 U자형 곡선)이 필요하다. 누적량을
경과시간으로 나누는 선형 정규화는 개장 직후를 과대추정하므로 채택하지 않았다.

> **다만 이 잔여 오차는 현재 우선순위가 아니다.** 거래량 배율 의존 신호는 점수 매도에만
> 쓰이는데 운영은 `SIGNAL_SELL_ENABLED=false` 라 그 경로가 꺼져 있다. 실제로 그 구성에서
> 장중을 켜면 국내형이 −17.6~−18.0%p 나빠지는데, 분해해 보면 비용이 3.3%, 진입가격은
> 오히려 개선이고 **악화의 거의 전부가 회전 증가에서 온다** —
> `docs/experiments/kr-intraday-degradation-2026-09-03.md`. 거래량 프로파일을 고쳐도
> 그 −17.6%p 는 그대로다. 장중매매 재활성화의 선결 과제는 **회전 억제**다.

### §17-2. 리플레이의 장중 경로 (v1.17.0)

`run_replay` 는 원래 하루 1사이클(마감 판정 → 다음 개장 체결)만 돌려 `evaluate_intraday`
를 **한 번도 호출하지 않았다**. 그래서 라이브 매도의 88% 가 검증 밖이었다. 이제
`Config().rules.intraday_enabled=True` 이면 리플레이도 장중 경로를 태운다.

```
python -m simcore --start 2026-01-01 --end 2026-09-01 --intraday-slices 8 --intraday-order low_first
python -m simcore --start 2026-01-01 --end 2026-09-01 --intraday-slices 8 --intraday-order high_first
```

**하루 안의 실행 순서** (라이브와 같다): `fill_open` → [슬라이스마다: `check_stops`(틱) →
`evaluate_intraday`] → `check_stops`(일봉 백스톱) → `evaluate_close`.

**경로 가정** — `simcore/intraday_path.py`. 일봉에는 경로 정보가 없다. (O,H,L,C)는 하루의 네
통계량일 뿐 고가·저가의 선후나 그 사이의 배회를 담지 않는다. 그래서 꺾은선을 **가정**한다:

| `order` | 경로 | 성격 |
|---|---|---|
| `low_first` (기본) | O → L → H → C | 저가를 먼저 밟아 손절이 더 걸린다(보수적). `check_stops` 의 기존 관례와 같은 방향 |
| `high_first` | O → H → L → C | 고가를 먼저 밟아 트레일링 피크가 먼저 올라간다 |

슬라이스 k(1..n)는 k/(n+1) 지점에 놓아 **구간 내부만** 담당하고, 종가 판정은
`evaluate_close` 에 맡긴다. 각 슬라이스의 `high`/`low` 는 샘플 지점이 아니라 **경로를 따라
실제로 지나간 구간의 극값**이다 — 두 스캔 사이에 저가를 찍고 되돌아온 날을 놓치면 손절
판정이 현실과 어긋난다. 거래량은 `V × k/(n+1)` 선형 누적이며, §17-1 의 제외 처리 덕에
신호에 미치는 영향은 제한적이다.

**이 하니스가 검증할 수 있는 것 / 없는 것**

- 할 수 있다 — 장중 로직의 *메커니즘*(스캔·휩쏘 캡·재매수 쿨다운·킬스위치가 도는가),
  규칙 변경의 *방향성*, 하루 1사이클 대비 *상대 비교*.
- 할 수 없다 — 정확한 손익. 실제 경로는 이 꺾은선보다 훨씬 배회하므로 체결가·체결 횟수가
  다르다. **한쪽 `order` 의 숫자만 인용하면 근사를 사실로 오인하는 것이다. 양방향을 모두
  돌려 그 폭(envelope)으로 보고할 것.**

**비용**: 슬라이스마다 종목별로 지표를 재계산한다(잠정봉이 매번 달라지므로 벡터화 불가).
히스토리는 `_INTRADAY_WINDOW`=160봉으로 잘라 호출당 비용을 묶어두었지만, 전체 시간은
슬라이스 수에 선형으로 늘어난다. 실무적으로 4~8 슬라이스를 권장한다.

**가격괴리율·지지/저항 지표(#27 배선 완료)**: `simcore/indicators.py`의 `disparity(close, period)`
(괴리율 = (종가−이동평균)/이동평균)와 `support_resistance(high, low, close, lookback)`(직전 구간
최저/최고 → 지지/저항)는 `evaluate_frame`(`simcore/signals.py`)에서 `SignalParams.disparity_period`
/`disparity_oversold`/`disparity_overbought`/`sr_lookback`으로 호출되어 G9(저항 돌파)·G8(괴리율
과매도 반등)·R20(괴리율 과열 확장)을 계산한다(§3·§4). 일봉 리플레이·장중(잠정봉) 양쪽 모두 같은
`evaluate_frame`을 통과하므로 두 경로가 동일하게 반영한다.

**미사용(reserved) 설정**: `TradeRules.intraday_disparity_period`/`intraday_sr_lookback`
(`Config().rules`)은 위 `SignalParams` 필드와 별개의 예약 필드로, 여전히 어떤 계산에도 소비되지
않는다(향후 장중 전용 튜닝을 위해 남겨둔 것).

**체결강도(execution strength) — KR 전용, 실서버 검증 전제**: `KisClient.execution_strength
(market, symbol)`는 KIS `inquire-price`(`FHKST01010100`) 응답의 `cttr` 필드를 매수 게이트에
쓴다 — 값이 `intraday_strength_buy_min`(기본 100.0) 미만이면 그 틱의 매수를 스킵한다.
**US는 미지원(`None` 고정 반환)** — 미국 종목은 체결강도 조건 자체를 건너뛰고 나머지 신호로만
판단한다(값이 `None`이면 조건 스킵, 조건을 만족한 것으로 위장하지 않되 차단도 하지 않음).
`cttr` 필드명·응답 스키마는 **KIS 공식 문서 기재값을 코드에 반영한 것으로, 실거래소 서버
응답으로 아직 검증되지 않았다** — 실서버 연동 시 필드명·값 스케일이 문서와 다를 수 있으므로
운영 전환 전 반드시 실응답으로 재검증해야 한다.

**휩쏘 캡·재매수 쿨다운·손절 예외**: 안전장치는 종목당 하루 단위로 적용된다
(`CharacterState.intraday_buys`/`intraday_sells`, 매 거래일 롤오버 시 초기화):
- 종목당 **장중 매수 ≤ `intraday_max_buys_per_symbol`(기본 3회)**, **장중 매도 ≤
  `intraday_max_sells_per_symbol`(기본 3회)** — 잦은 신호 뒤집힘(휩쏘)으로 하루 안에
  과도하게 왕복 매매하는 것을 막는다.
- 매도 후 같은 종목 재매수는 **`intraday_reentry_cooldown_min`(기본 30분)** 경과 전엔
  차단된다(`intraday_last_sell_ts` 기준).
- **손절(`R7`)·트레일링 스탑(`R10`)·강제청산 2종(`R18`, `R5+R23`)은 이 매도 캡을 거치지
  않는 예외**다 — 리스크 관리가 휩쏘 캡보다 항상 우선한다.

**킬스위치(당일 −5%)**: 그날 시작 자산(`intraday_day_start_equity`, 그날 첫 스캔에서
고정) 대비 현재 자산이 `intraday_daily_loss_halt_pct`(기본 −5%) 이하로 떨어지면 그 캐릭터는
**그날 신규 매수를 중단**한다. **매도(청산·손절·트레일링·강제청산)는 계속 동작** — 킬스위치는
손실을 더 키우는 신규 진입만 막고, 보유 종목을 위험에 방치하지 않는다.

**비용 정직 적용**: 장중 체결도 새 체결 경로를 만들지 않고 기존 `Engine._buy`/`_sell`(수수료·
세금·FX 환전 수수료·슬리피지)을 그대로 경유한다 — 일봉 매매와 동일한 비용 모델(§10)이며
장중이라고 비용을 생략하거나 근사하지 않는다.

**부분 실패 스킵**: 시세·호가·체결강도 조회가 실패한 종목은 그 스캔만 스킵하고 다음 스캔에서
재시도한다. 데이터가 없는 조건(예: US 체결강도)은 그 조건만 스킵할 뿐, 종목 전체 평가를
건너뛰지 않는다.

**리플레이/백테스트 미포함 — 라이브 전용, 관측 목적**: `evaluate_intraday`/`on_intraday`는
리플레이 엔진(`replay.run_replay`)·백테스트 경로에 연결되지 않는다. 장중 매매의 과거 재현·
walk-forward 검증은 이 구현 범위 밖이며, 현재는 **실시간 라이브(PAPER)에서 실동작을 관측**하는
것이 목적이다(감사 로드맵 3단계 전략 검증과는 별개 — 3단계 통과 전 실주문 코드는 여전히 없다).

### §17-3. 장중 회전 억제 브레이크

`docs/experiments/kr-intraday-degradation-2026-09-03.md` 에서 장중 악화의 원인이 **회전
증가**로 특정됐다. 매도 구성을 뜯어보면 원인이 더 좁혀진다 — 현재 운영 구성
(`signal_sell_enabled=false`)에서 장중 경로가 만들어내는 것은 사실상 **매수뿐**이다:

| | 장중 OFF | 장중 ON (4슬라이스) |
|---|---|---|
| 매수 | BUY 117 | **INTRADAY_BUY 104** + BUY 40 |
| STOP_LOSS | 49건 −49.1M | **60건 −60.6M** |
| TRAILING_STOP | 33건 +55.6M | 55건 +85.5M |
| 강제 SIGNAL_SELL(R18·R5+R23) | 30건 **+36.3M** | 21건 **+11.3M** |
| INTRADAY_SELL | — | **2건** |
| 당일 청산 | 12건 | **30건** |

장중 매도는 2건뿐이다. 즉 장중 경로를 켜는 것은 실질적으로 **"장중에도 산다"** 는 뜻이고,
그렇게 연 포지션이 같은 날 저가에 노출돼 손절이 늘고(49→60), 수익을 내던 강제매도 구간을
밀어낸다(+36.3M → +11.3M).

이를 직접 누르는 손잡이 둘 (기본값은 기존 동작 그대로):

| 파라미터 | 기본 | 뜻 |
|---|---|---|
| `intraday_buy_enabled` | `True` | `False` = **장중 매수 금지**. 장중 매도·손절·트레일링은 그대로 — 비대칭 구성 |
| `intraday_max_buys_per_day` | `0` | 캐릭터별 **하루 장중 매수 상한**(0 = 무제한). 종목별 캡 `intraday_max_buys_per_symbol` 과 달리 전 종목 합산 |

운영 전환은 `.env` 의 `INTRADAY_BUY_ENABLED` / `INTRADAY_MAX_BUYS_PER_DAY`. 차단 사유는
의사결정판에 `"장중매수OFF"` / `"일일매수상한"` 으로 기록된다.

| `trailing_intraday_update` | `True` | `False` = 트레일링 peak/잠금선을 **마감에서만** 갱신. 손절 체크 자체는 장중에도 계속 |

**검증 결과 — 듣는 것은 세 번째뿐이다.** 앞의 두 브레이크는 개선을 만들지 못했고(장중 매수를
아예 막으면 오히려 −13.1%p), 경로 가정을 바꾸면 순서가 뒤집혀 잡음에 묻힌다. 반면
`trailing_intraday_update=False` 는 3개 구간 × 경로 양방향 **6개 조합 전부**에서 국내형을
**+9.6 ~ +18.8%p** 개선한다.

이유: 라이브는 `tick` 잡이 5분마다 돌며 `_update_trailing` 으로 잠금선을 **장중에 계단식으로
올린다**. 그러면 같은 날 되돌림이 그 올라간 선을 때려 청산된다. `run_replay` 는 하루 1회만
판정해 이걸 모사한 적이 없었다 — **백테스트가 라이브보다 관대**했다는 뜻이고, 지금까지의
국내형 성과는 그만큼 과대평가돼 있었다.

끄면 결과가 하루-1회 기준선과 소수점까지 일치한다. 즉 **라이브를 이미 검증된 일봉 동작에
맞추는 변경**이지 새 알파가 아니다.

상세: `docs/experiments/intraday-turnover-brakes-2026-09-03.md`.

## 18. 워크포워드(롤링 아웃오브샘플) 검증 — 감사 로드맵 3단계

전략 성과가 한 번의 운 좋은 구간이 아니라 여러 시간 구간에서 일관되는지 정직하게 보여주는
하니스다. `simcore/walkforward.py`. 신규 의존성 없이 기존 `replay.run_replay`와
`metrics.risk_metrics`를 그대로 재사용한다.

**정직한 범위 한정(non-goal)**: 아래 `run_walkforward`는 엔진 파라미터(`Config`)를 **전 폴드
공통 고정**하고 폴드별 재적합을 하지 않는다 — 이는 엄밀한 워크포워드 최적화(WFO)가 아니라
**롤링 OOS 평가**다. 신호는 인과적(과거만 참조)이라 번들 전체 히스토리를 워밍업으로 써도
lookahead가 없으며, 각 폴드의 시뮬레이션은 test 구간에서 콜드스타트(초기자금)로 시작한다.

**진짜 WFO + 과적합확률(PBO) — 구현됨(#30)**: 폴드별 train 구간에서 파라미터를 그리드
탐색(IS)하고, 선택된 파라미터로 test 구간을 평가(OOS)하는 진짜 워크포워드 최적화와, IS에서
최적이던 파라미터가 OOS에서도 우수한지 폴드 이분 조합으로 검증하는 과적합확률(PBO, CSCV
경량판)이 `simcore/walkforward.py`의 `generate_opt_folds`/`run_wfo`/
`probability_of_backtest_overfitting`으로 구현되어 있다. 자세한 내용은 아래 "워크포워드
최적화(WFO) + PBO" 절 참조. **여전히 후속 과제로 남는 것**: purge/embargo와 ≥100개 폴드
분할 경로를 갖춘 완전한 CPCV(현재 PBO는 폴드 이분 조합만 쓰는 경량판), Deflated/Probabilistic
Sharpe Ratio(DSR/PSR).

**폴드 생성**(`generate_folds(start, end, test_days=63, step_days=63, warmup_days=120)`):
`[start, end]`를 `step_days` 간격으로 타일링해 `test_days` 길이의 test 구간을 만든다. 첫
`test_start`는 `start + warmup_days` 이상(지표 워밍업 확보). 마지막 폴드의 `test_end`는
`end`를 넘지 않게 자르고, 잘려서 창 길이가 `test_days // 2` 미만이면 그 폴드는 제외한다.

**평가**(`run_walkforward(config, bundle, folds)`): 폴드마다 `run_replay(config, bundle,
fold.test_start, fold.test_end)`를 호출해 캐릭터별 `{twr, mdd, sharpe, win_rate, n_trades}`를
기록한다(`sharpe`는 `risk_metrics`, `win_rate`는 `risk_metrics`에 키가 없어 SELL 행의
`realized_pnl > 0` 비율로 직접 계산). 폴드 구간에 거래일이 없어 `run_replay`가
`ValueError`를 던지면 그 폴드는 건너뛰고(로그) 계속 진행한다.

**집계**(폴드 간 일관성, 캐릭터별): `mean_twr`/`std_twr`, `pct_profitable_folds`(twr>0 폴드
비율), `mean_sharpe`, `worst_mdd`(폴드 중 최악의 낙폭 절대값), `n_folds`.

**CLI**: `python -m simcore.walkforward --start YYYY-MM-DD --end YYYY-MM-DD [--test-days
--step-days --warmup-days --kr-top --us-top --cache --out]` — 번들을 전체 구간으로 1회 로드
후 폴드별·집계 표를 콘솔에 출력하고, `--out` 지정 시 마크다운 리포트로도 저장한다.

### 18.1 워크포워드 최적화(WFO) + 과적합확률(PBO) — #30

`--wfo` 플래그로 위 롤링 OOS 검증과 별도 모드를 켠다. 폴드는 `generate_opt_folds(start, end,
train_days, test_days, step_days)`로 train(파라미터 탐색용)+test(OOS 평가용) 쌍으로
타일링한다(첫 `test_start = start + train_days`, `train_start = test_start - train_days`).

`run_wfo(config, bundle, folds, grid, objective="twr", character="국내형")`은 폴드마다
① train 구간에서 `grid`(현재는 `buy_score_min` 단일 축)를 전수 탐색해 objective(`twr` 또는
`sharpe`) 기준 최적값을 고르고(IS), ② 그 값으로 test 구간을 평가한다(OOS). 그리드값 평가 중
`run_replay`가 `ValueError`(거래일 없음 등)를 던지면 그 값은 `-inf`로 기록하고 로그를 남긴
뒤 계속 진행한다(그리드 전체가 실패하지 않는 한 폴드 자체는 건너뛰지 않는다).

**WFO 효율**(`mean(OOS) / mean(IS-best)`)은 `is_best_perf`와 `oos_perf`가 **둘 다 유한한
폴드만 페어링**해서 평균 낸다(`_wfo_efficiency` 순수 헬퍼) — 한쪽만 그리드 전체 실패로
`-inf`가 된 폴드를 분자·분모에서 서로 다른 폴드 집합으로 독립 필터링하면 비율이 무의미해지기
때문이다. 페어링된 폴드가 없거나 `mean(IS-best) == 0`이면 `float("nan")`을 반환한다(0.0이
아님 — PBO의 "계산 불가 시 nan" 관례와 일관).

**과적합확률(PBO)**은 `probability_of_backtest_overfitting(is_matrix, oos_matrix)`로
계산한다 — López de Prado CSCV(Combinatorially Symmetric Cross-Validation)의 경량판으로,
폴드를 두 동일 크기 그룹으로 나누는 모든 조합에서 "IS 최적 파라미터가 OOS 순위 하위 절반에
드는 빈도"를 잰다. 폴드 수·그리드 수가 2 미만이면 `nan`.

**CLI**: `python -m simcore.walkforward --start YYYY-MM-DD --end YYYY-MM-DD --wfo
[--train-days --grid 12,14,16,18,20 --objective twr|sharpe --character 국내형 --test-days
--step-days --kr-top --us-top --cache --out]`.
